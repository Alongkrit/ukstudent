
UK STUDENT SUPPORT
Frontend Specification Document
Screens, navigation, design system and component structure across mobile app, web app and Admin console
Version 1.1  |  August 2026  |  Status: Draft for build  |  Covers: iOS, Android and Web
Team size: 2 (Backend/Full-stack + Frontend/Mobile)

1. Overview
There are four frontend surfaces: the Student & Expert mobile apps (React Native/Expo, one codebase with role-based navigation), the Student & Expert web app (Next.js, the same product experience in a browser), and the Admin Console (React web app, internal use only). This document specifies the screen inventory, navigation structure, design system and component/state approach needed to build all four.
The mobile app and web app are not two different products — they are the same feature set (everything in Section 4.1/4.2) on two platforms. A student can sign up on the website, submit a request from a laptop, and continue the conversation in the mobile app; both read and write the same backend described in the Technical Architecture Document.

2.3 Typography
Font family: Inter (or system default fallback) for both mobile and web — clean, highly legible, free.
Scale: H1 28/34, H2 22/28, H3 18/24, Body 16/24, Caption 13/18, Button label 16/20 (size/line-height in px).
Weights: Bold (700) for headings and emphasis, Regular (400) for body, Medium (500) for buttons/labels.
2.4 Spacing & Layout
8px base spacing unit (4/8/16/24/32/48) applied consistently across padding, margins and gaps.
Cards use 12px corner radius, subtle shadow, 16px internal padding — matching the rounded, friendly feel of the marketing site's chat bubbles and service cards.
Minimum touch target 44x44pt on all interactive elements (accessibility requirement, see Section 6).

3. Information Architecture & Navigation
3.1 Student App Navigation
Bottom tab navigator with 5 tabs, each a stack navigator:
Home — dashboard, active request status, quick-start service picker
Requests — list of past & active requests
Chat — list of conversations (badge for unread)
Blog — study tips articles
Profile — account, payment methods, settings, support
3.2 Expert App Navigation
Bottom tab navigator with 4 tabs (role-differentiated build of the same app shell):
Dashboard — availability toggle, incoming request alerts, today's stats
Requests — active/accepted requests
Chat — conversations with students
Profile — earnings, payout history, subjects/qualifications, settings
3.3 Student & Expert Web App Navigation
The web app mirrors the mobile tab structure but adapts it to browser conventions:
Desktop / tablet (≥ 768px): persistent left sidebar with the same sections as the mobile tabs (Home, Requests, Chat, Blog, Profile for students; Dashboard, Requests, Chat, Profile for experts), plus a top bar with notifications and account menu.
Mobile web (< 768px): bottom tab bar identical in structure to the native app, so the experience feels familiar to anyone switching between web and app.
Public, unauthenticated routes exist for marketing/SEO purposes and link into the authenticated app: a public Service catalogue, public Blog (list + detail), and Sign up / Log in — these correspond to the existing marketing site's Home, Services, Blog and Get the App navigation, now served as real pages rather than static marketing copy.
3.4 Admin Console Navigation
Left sidebar layout (standard admin pattern):
Overview — key metrics (active requests, pending expert applications, GMV)
Users — student & expert directories, suspend/ban actions
Expert Applications — verification queue
Requests — monitor/search all requests, dispute intervention
Payments — transactions, refunds, expert payout batches
Moderation — reported conversations queue
Blog CMS — create/edit/publish articles
Settings — service categories, admin team accounts

5. State Management & Data Fetching
Server state (requests, chats, profiles): React Query (TanStack Query) for caching, background refetch, optimistic updates on actions like sending a message or accepting a request.
Real-time chat state: Socket.IO client, messages appended to the React Query cache on receipt so the chat list and thread stay in sync.
Local/UI state: React's built-in useState/useReducer — no need for a separate global store given the app's size.
Auth state: a small context provider holding the current user + tokens, backed by Expo SecureStore for persistence.
Forms: React Hook Form + Zod schema validation, shared validation schemas between the New Request flow and the Expert Apply flow where fields overlap.
6. Accessibility & Responsiveness
WCAG 2.1 AA colour contrast minimums for all text/background combinations in the palette.
All interactive elements have accessible labels for screen readers (VoiceOver/TalkBack); icons paired with text or aria-label equivalents.
Minimum 44x44pt touch targets; form fields support dynamic text sizing.
Admin Console supports desktop breakpoints down to 1280px; mobile use of Admin is out of scope for MVP.
Student/Expert mobile apps support standard phone screen sizes (iOS SE up to Pro Max, common Android sizes); tablet layout is a post-MVP enhancement.
Student/Expert web app is responsive across three breakpoints: mobile web (< 768px, bottom tab layout matching the app), tablet (768–1024px), and desktop (> 1024px, sidebar layout) — built mobile-first and progressively enhanced.
Public web pages (Home, Service Catalogue, Blog) are server-rendered (Next.js SSR/SSG) for SEO and fast first-paint, since they are the primary discovery surface for new users arriving from search or social.
7. Error, Loading & Empty States
Every data-fetching screen defines three states explicitly: loading (skeleton placeholders, not spinners, for list screens), error (retry action + friendly message), and empty (illustration + guidance, e.g. “No requests yet — start one now”).
Network failures on submit actions (new request, send message, payment) show inline retry rather than losing the user's input.
Offline banner shown app-wide when connectivity drops; chat messages queue locally and send on reconnect.
