
UK STUDENT SUPPORT
Technical Architecture Document
System design & technology stack for the UK Student Support mobile platform
Version 1.0  |  August 2026  |  Status: Draft for build
Team size: 2 (Backend/Full-stack + Frontend/Mobile)

1. Overview & Purpose
UK Student Support is a mobile-first platform that connects UK university students with vetted academic experts for on-demand help across assignments, homework, dissertations, exam preparation, proofreading and programming. Students submit a request describing their subject, deadline and supporting documents; the platform matches them with an available expert; the pair communicate through in-app chat; and the engagement is closed out with a rating and payment.
This document defines the technical architecture that a two-person team (one backend/full-stack engineer, one frontend/mobile engineer) can realistically design, build and operate. Every choice below favours managed services and a single deployable backend over a distributed microservice estate, so that the two-person team spends its time on product features rather than infrastructure.
1.1 Goals
Ship a working MVP (Student app + Expert app + lightweight Admin console) within a small team's capacity.
Keep operational overhead low: one primary backend service, one primary database, managed third-party services for chat/notifications/payments/storage.
Design for UK data protection (UK GDPR) from day one, since the product processes student personal data and academic work.
Keep the architecture modular internally (clear service boundaries in code) so it can be split into separate services later if the team grows.
1.2 Non-Goals (for MVP)
Native desktop apps — the web experience is a responsive browser app (not an installable desktop client).
Video/voice calling between student and expert — text chat and file sharing only for MVP.
Automated plagiarism/AI-content detection — handled as a manual moderation policy in v1 (see Security & Access Document).
Multi-currency/international expansion — GBP only, UK-registered experts only.
2. High-Level Architecture
UK Student Support ships on three surfaces — a Student & Expert mobile app, a Student & Expert web app, and an internal Admin web console — all talking to a single backend API, which relies on a managed relational database and a small set of third-party managed services. Mobile and web are two presentation layers over the same product: the same student can start a request on the website and finish the conversation in the mobile app, because both read/write the same backend.

2.3 One Backend, Three Frontends — and Why This Is Realistic for 2 People
A single NestJS backend serves mobile, web and admin identically — the same REST endpoints and the same Socket.IO gateway are used by all three, so there is exactly one place matching/chat/payment logic lives, regardless of platform.
React Native (Expo) covers iOS + Android from one codebase; Next.js covers the web app. Both are React + TypeScript, so the frontend engineer reuses business logic (API client, validation schemas, formatting helpers) as a shared package between the two, and only the UI layer (native components vs. HTML/CSS with Tailwind) differs.
The web app is built responsive-first (mobile-web breakpoint down to ~360px, tablet, desktop) so it also serves as the mobile-browser fallback for anyone who lands on the site without the native app installed — this satisfies the marketing site's existing “Get the App” / “Open in App” links even before a user downloads anything.
Stripe Connect removes the need to build a custom ledger/payout engine — Stripe handles KYC for experts, holds funds, and pays out on a schedule, with equivalent SDKs on both web and mobile.
Managed Postgres + Redis removes database administration; both providers offer automated backups, so no DBA is required.
Socket.IO works natively over both native WebSocket (mobile) and browser WebSocket (web) from the same NestJS gateway — no separate real-time implementation needed per platform.

3.2 Request Lifecycle (state machine)
submitted — student has filled the request form and attached files.
matching — backend is searching for/notifying eligible experts (subject match + availability).
matched — an expert accepted; conversation is created and both parties notified.
in_progress — chat is active until the student marks the request resolved or the deadline passes.
completed — student confirms completion; triggers review prompt and finalises payment capture/expert payout accrual.
cancelled — student or system cancels (e.g., no expert found within matching window); refund path if pre-paid.

4.2 Conventions
JSON request/response bodies; snake_case for DB columns, camelCase in API payloads (mapped at the service layer).
Pagination via ?page= & ?limit=, capped at 50 items per page.
Standard error envelope: { statusCode, error, message, requestId }.
Idempotency keys required on POST /payments/create-intent to avoid duplicate charges on client retry.
4.3 Cross-Platform Auth: Mobile vs. Web
The same auth endpoints (Section 4.1) serve both platforms, but tokens are stored differently because a browser and a native app have different safe-storage primitives:
Mobile app: JWT access + refresh tokens stored in Expo SecureStore, sent as a Bearer header on every request (as described in the Security & Access Document).
Web app: refresh token stored as an httpOnly, Secure, SameSite=Lax cookie (not accessible to JavaScript, mitigating XSS token theft); short-lived access token kept in memory only and attached as a Bearer header. This is the standard safer pattern for browser clients.
CSRF protection is required on the web app's cookie-based refresh endpoint (double-submit token or SameSite cookie policy) since mobile's header-based auth is not vulnerable to CSRF but the web cookie flow is.
CORS on the backend allow-lists the web app's origin(s) explicitly (production domain + staging domain); the mobile app calls the API directly and is not subject to CORS.
5. Matching & Real-Time Chat
5.1 Matching Algorithm (MVP — rules-based, not ML)
On request submission, backend queries expert_profiles for verified experts whose subjects[] intersects the request's subject and whose availability flag is on.
Push notification + in-app alert sent to the top N (e.g. 5) matching experts simultaneously (“broadcast” model).
First expert to accept via POST /requests/:id/accept wins the request; a DB row-level lock/transaction prevents double-acceptance.
If no expert accepts within a configurable matching window (e.g. 15 minutes), the pool is widened (drop subject specificity to “general”) and the student is shown a status update; after a second window, the student is offered manual cancellation/refund.
5.2 Chat Delivery
Socket.IO server co-located in the NestJS process for MVP; Redis adapter used from day one so it is trivial to scale to multiple backend instances later.
Messages are persisted to Postgres synchronously before being emitted, so REST history and WebSocket stream never disagree.
Attachments are uploaded directly to S3 via a pre-signed URL obtained from the backend, then the resulting object URL is sent as a normal message.

6.1 CI/CD
GitHub Actions: lint + type-check + test on every PR; deploy to staging on merge to main; manual promotion (tag) to production.
Backend deployed as a container to a managed platform (e.g. Render, Railway, or AWS ECS Fargate) — chosen to avoid the team managing raw servers/Kubernetes.
Web app (Next.js) deployed to Vercel (or Netlify) with automatic preview deployments per PR — zero-config CI/CD for the frontend engineer, and free/cheap at MVP traffic levels.
Mobile builds via EAS Build (Expo) producing signed iOS/Android binaries; EAS Update for OTA JS-only patches between store releases.
Database migrations managed with Prisma Migrate (or TypeORM migrations), run automatically as a pre-deploy step in CI.
6.2 Suggested Backend Folder Structure
src/modules/auth, src/modules/users, src/modules/experts, src/modules/requests, src/modules/matching, src/modules/chat, src/modules/payments, src/modules/notifications, src/modules/admin, src/modules/blog
Each module owns its controller, service, DTOs and Postgres repository — keeping clear internal boundaries even though it deploys as one service, so it can be split out later if needed.
7. Scalability, Reliability & Observability
MVP target: a few hundred concurrent users, low thousands of requests/day — comfortably handled by a single small backend instance plus a read replica added only if reporting queries start impacting latency.
Redis-backed BullMQ queues handle anything that shouldn't block the request/response cycle: push notification dispatch, matching-window timeouts, payout batch jobs, review-reminder emails.
Sentry captures backend exceptions and mobile crashes; a shared Slack/Discord alert channel is enough monitoring for a 2-person team at this stage.
Daily automated Postgres backups with 7–30 day retention (provider default) and a documented manual restore runbook.
Health check endpoint (GET /health) polled by the hosting platform for zero-downtime rolling deploys.
