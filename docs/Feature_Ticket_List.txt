
UK STUDENT SUPPORT
Feature Ticket List
Epics and build-ready tickets for the UK Student Support MVP — mobile app + web app
Version 1.1  |  August 2026  |  Status: Ready for sprint planning  |  Covers: iOS, Android and Web
Team size: 2 (Backend/Full-stack + Frontend/Mobile)

How to Read This Backlog
Tickets are grouped into epics matching the architecture and frontend specs. Each ticket lists an owner suited to a 2-person team: BE (backend/full-stack engineer), FE (frontend engineer, covering both mobile and web), or Both. Estimates are rough sizes in engineer-days assuming the stack chosen in the Technical Architecture Document. Priority: P0 = required for MVP launch, P1 = important but can follow shortly after, P2 = nice-to-have / post-MVP.
Platform coverage: the product ships on mobile (iOS + Android) and web from day one. Epics 1–6 below describe functionality that is built twice — once in the React Native app, once in the Next.js web app — against the same backend endpoints. Rather than duplicate every ticket per platform, each functional ticket's estimate assumes both a mobile and a web implementation; Epic 9 (Web App Platform) covers the web-specific setup and the public marketing/SEO pages that don't exist on mobile.

Summary
Total scope: 9 epics covering authentication, expert vetting, the request/matching engine, real-time chat, payments, reviews/notifications/blog, the Admin console, security/platform foundations, and the web app platform. P0 tickets represent the minimum required to launch a working two-sided marketplace on both mobile and web (student request → expert match → chat → payment → review); P1/P2 tickets can follow in the weeks after initial launch.
Suggested sequencing for a 2-person team: Epic 1 (Auth) → Epic 2 (Expert onboarding) → Epic 3 (Requests & Matching) → Epic 4 (Chat) in parallel with Epic 8 security foundations → Epic 5 (Payments) → Epic 7 (Admin) → Epic 6 (Reviews/Notifications/Blog polish), with Epic 9 (Web platform) started as soon as WEB-1/WEB-2/WEB-3 can run in parallel with the mobile build of Epics 1–3, since both platforms hit the same backend.
A pragmatic MVP sequencing option for a 2-person team is to ship mobile first end-to-end, then port the same screens to web using the shared API client/validation package (Epic 9) — this avoids building every screen twice in parallel and lets the web app benefit from UX decisions already validated on mobile.
Admin console tickets (Epic 7) can be built incrementally alongside other epics since each admin screen unlocks the workflow behind a P0 ticket elsewhere (e.g. ADM-1 verification queue is required before EXP-5 approve/reject can be tested end-to-end).
